# Rentivo — Project Guide for Agents

## Project Overview

**Rentivo** is a peer-to-peer marketplace exclusively for camera, smartphone, and lens rentals. It connects equipment owners ("hosts") with renters for photography, videography, travel, content creation, events, and short-term projects. Philippine market: ₱ pricing, GCash/Maya payments, cities like Manila, Cebu, Davao.

The project started from a Claude Design prototype (`Rentivo.html` — still the canonical visual reference) and is now a working full-stack app: Next.js frontend, hosted Supabase backend (auth, database, storage), and PayMongo payments.

## Architecture Notes

- **Auth**: Supabase cookie sessions via `@supabase/ssr`; `src/proxy.ts` guards `/dashboard`, `/host`, `/book`, `/messages`. Signup enforces password policy client + server; hosted project requires email confirmation. **Google OAuth is enabled and verified working (2026-07-19)** — configured entirely in dashboards, nothing in this repo: a Google Cloud OAuth web client (redirect URI `https://prfizruuqwvteqovuqco.supabase.co/auth/v1/callback`) plus the Supabase Google provider (Client ID/Secret) and `http://localhost:3000/auth/callback` in the redirect allow-list. The consent screen is published (In production, External — any Google account works; basic scopes, no Google verification needed). Supabase Site URL is the prod domain, and the allow-list covers `/auth/callback` + `/reset-password` on both localhost and prod (the Google-side redirect URI never changes per environment).
- **Data layer**: server components call `src/lib/listings.ts`; client pages use hooks (`useBookings`). Host joins use explicit FK hints (`profiles!listings_host_id_fkey`).
- **Booking lifecycle**: `create_booking` RPC is the *only* insert path (direct inserts revoked — see the 038/039 note below for a security regression that briefly reopened this, caught by review). It computes all amounts server-side (5% service fee on the rental only, promo discount on rental fee only, delivery fee added on top when the renter chooses delivery — see the pricing note below) and creates the booking `pending` + `unpaid`. `mark_booking_paid` (service-role only, idempotent) is the only path to `paid`; Instant Book flips to `confirmed`, which triggers availability blocking. Renters may cancel only pending bookings; host transitions are trigger-enforced (`pending→confirmed→active→completed`). Host accept/decline **and** renter cancel both go through `POST /api/bookings/[id]/respond` (not a direct client table update) — RLS + the trigger still decide who's allowed which transition, the route just adds a server context to refund from and email from afterward. **Delivery fee** (038): `listings.delivery_fee` is nullable (`null` = not offered, `0` = free, `>0` = flat fee); `bookings.delivery_fee` is `not null default 0`. `create_booking` reads the fee off the *locked* listing row (never a client parameter), rejects a delivery booking if the host doesn't offer it, and excludes the fee from the service-fee base — it's a pass-through to the host, not commission. `request_payout()` pays hosts `rental_fee + delivery_fee`. `src/lib/pricing.ts` mirrors this math client-side for the checkout UI.
- **Listing publication** (037): a new listing from an unverified host is forced to `is_draft = true` by a `before insert` trigger, and an unverified host is blocked by a `before update` trigger from flipping their own draft to published (the service role is exempt) — enforced in the database because `authenticated` holds `insert`/`update` on `listings` and a client-side gate would be bypassable. `review_verification_request()` auto-publishes a host's pending listings on approval, after setting `is_verified`. Every public read path (RLS, `searchListings`, `create_booking`, detail/host-profile queries, `increment_listing_view`) already excludes `is_draft` rows, so this reuses existing plumbing rather than adding new state.
- **Refunds** (`src/lib/refunds.ts`): `refundBooking()` runs on every cancellation of a paid booking, from `/api/bookings/[id]/respond` — no-ops (`refunded: true`) if there was nothing to refund, so callers never pre-check payment_status. It's non-fatal: a failed PayMongo refund never blocks the cancellation itself, it just leaves `payment_status` at `paid` for manual follow-up (never falsely marks `refunded`). `mark_booking_refunded` (014, service-role only, idempotent) is the only path to `payment_status='refunded'`, mirroring `mark_booking_paid`. **PayMongo refunds draw against the merchant's payout balance** — a fresh test-mode account has none, so refunds will fail with `"Refund amount is greater than the available payout amount"` until the account has processed enough live/test volume to have a balance; this is documented PayMongo behavior, not a bug here (verified live: the refund call correctly reaches PayMongo with the right payment id/amount and is correctly rejected, and the booking still cancels either way).
- **Payments**: `POST /api/payments/checkout` creates/reuses the booking, creates a PayMongo intent for the server-computed total, attaches the payment method (cards tokenized in-browser with the public key — card data never touches our server; e-wallets server-side), and returns `paid` or a redirect URL. `/book/complete` verifies the intent after GCash/Maya/3DS redirects; `POST /api/webhooks/paymongo` (`payment.paid`, HMAC-verified) is the production source of truth. No PayMongo keys → simulated payments (dev only, still requires `SUPABASE_SECRET_KEY`). **Card payment methods must include `billing.email`** (PayMongo API requirement discovered live — 400s without it); the card form auto-fills it from the signed-in user's account email rather than asking for it again.
- **Notifications**: written *only* by security-definer triggers on `bookings` (request/confirmed/cancelled/completed/paid) and `reviews` (received) — never inserted by clients, so RLS only needs to scope reads and `is_read` updates to the owning user. `useNotifications` subscribes via Realtime; powers the navbar bell badge and the dashboard page.
- **Messaging**: threads are derived from bookings the signed-in user is party to (`useThreads`), not a separate conversations table — a thread is a booking with ≥1 message. `useConversation` subscribes per-booking via Realtime and auto-marks incoming messages read while open. "Message Host"/"Message" CTAs deep-link to `/dashboard/messages?booking=<id>`. Messages can carry one image (message-images public bucket, `<uid>/<uuid>.<ext>` paths, 10 MB, upload in `useConversation.send()` before insert).
- **Analytics**: `listings.view_count` increments via the `increment_listing_view` RPC (security definer, callable by anon+authenticated) called from `ViewTracker` on the listing detail page — a plain counter, not a deduped events log.
- **Identity verification**: `verification_requests` table (015) — real uploads to the existing private `verification-docs` bucket, one row per submission. Review is a single `review_verification_request(request_id, approve, notes)` RPC (service-role only), driven through the `/admin/verifications` panel (see the admin-panel Status entry) rather than the SQL editor directly — approving flips `profiles.is_verified` **and**, since 037, auto-publishes that host's pending (`is_draft`) listings. Users can never self-approve (only `select`/`insert` granted, RLS has no update policy so any client-side status write is a no-op). Wired in two places: `Step6Verify` in the host wizard (files stay local `File` state until the wizard's final submit, matching how photos already work) and a standalone `VerificationCard` in Settings (uploads immediately) for renters or hosts checking/resubmitting outside the wizard. A host's listings stay hidden (`is_draft = true`) until this approval — see the listing-publication note above.
  Before the human `/admin` review, both upload tiles now run an on-device face check (`src/lib/id-validation.ts`, `validateIdDocument`/`validateSelfie`) — see the "ID/selfie upload validation" Status entry below for what this catches and, just as importantly, what it doesn't.
- **Transactional email** (`src/lib/email.ts`, Resend): `notifyBookingPaid()` fires from all three places a booking can become paid (checkout route's simulated + real-charge branches, `/book/complete`'s redirect-verification, and the webhook — each guarded so it only fires on the actual unpaid→paid transition) and sends the host a "new request/instant booking" email plus the renter a "confirmed" or "payment received, awaiting host" email depending on `is_instant_book`. `notifyBookingResponded()` fires from `POST /api/bookings/[id]/respond` for both confirm and cancel — cancellation is asymmetric by design: it notifies whichever party *didn't* initiate it (host declining → emails the renter; renter cancelling → emails the host), and the copy reflects whether the refund actually succeeded (`refundBooking()`'s result) rather than always claiming one will happen. No `RESEND_API_KEY` → each call no-ops with a console log instead of failing; verified live by checking those log lines against triggered flows.
- **Pickup map**: `PickupMap` (`src/components/listings/PickupMap.tsx`) renders an interactive Leaflet map + OpenStreetMap tiles, pinned at the listing's **city center** (`src/lib/ph-locations.ts`, a static PH city/province → lat-lng table — no geocoding API, no ongoing cost, no account needed anywhere). Deliberately coarse: matches the existing privacy copy ("exact pickup address is shared after your booking is confirmed"). Switched off Mapbox mid-build after their signup flow rejected the account twice (unrelated to this repo) — OSM/Leaflet needs zero signup, which is why it's the default here rather than a hosted static-maps API. Leaflet touches `window`/`document`, so `PickupMapLeaflet.tsx` is `next/dynamic`-imported with `ssr: false` from the (client) `PickupMap.tsx` wrapper — don't import it directly into a Server Component, and don't drop the `ssr:false` guard. Note `listings.latitude`/`longitude` columns exist in the schema (001) but are unused/always null — don't wire them into any public-facing map without a privacy review, since unlike the city lookup they could hold an exact address if ever populated by a future feature. The search page reuses the same Leaflet/OSM stack via SearchMap/SearchMapLeaflet (src/components/search/) — city-grouped markers over the filtered results, HTML-escaped popup content, same ssr:false dynamic-import rule.
- **Payouts**: `payout_accounts` (one per host, replace-not-append) / `payout_requests` / `payout_items` (020) — same manual-admin-review shape as identity verification: hosts write only through `set_payout_account()`/`request_payout()` (security-definer RPCs scoped to `auth.uid()`), and every status transition (`verified`/`rejected`/`paid`/`failed`) is a `service_role`-only RPC run manually from the SQL editor. `request_payout()` itemizes exactly which completed+paid bookings a request covers into `payout_items`, so a booking can never be claimed by two payout requests at once, and a failed request's bookings automatically become eligible again; 021 rewrote it to compute the amount and itemization from a single CTE so both come from one atomic snapshot (the original two-SELECT version had a race window). No live PayMongo disbursement — money movement itself is manual, matching this project's existing "verify live, no automated bank transfer" posture.
- **Account deletion** (`src/app/api/account/delete/route.ts`, Settings' Danger Zone): self-service, service-role only, and deliberately *not* a hard delete — `bookings`/`reviews`/`messages` reference `profiles` without `on delete cascade` while `profiles.id → auth.users` *does* cascade, so a real auth delete would wipe the counterparty's history. Instead the route anonymizes `profiles` into a "Deleted User" tombstone, deactivates + de-addresses the host's `listings`, nulls `bookings.delivery_address`, scrubs `payout_accounts` in place (its FK from `payout_requests` has no `on delete` clause), deletes only the rows nobody else depends on (`verification_requests`, `notifications`, `wishlist`, `recently_viewed_listings`), and finally soft-deletes the auth user via `deleteUser(uid, true)` — which blocks login while keeping the `auth.users` row, so the cascade never fires. Two eligibility gates run first (400): any booking in `pending`/`confirmed`/`active`, and any `pending` `payout_requests` row — deleting during either would strand an in-flight rental or real owed money. Storage cleanup (`avatars`, `verification-docs`, `payment-qr-codes`) runs *before* the row deletes, since `verification_requests` holds the only record of the doc paths, and is non-fatal (log-and-continue) so a storage hiccup never blocks the auth soft-delete; `message-images` is left alone on purpose, as those belong to the counterparty's retained conversation. The anonymize update also nulls `qr_payment_url`/`qr_payment_label` (028) — the label is the host's real name + mobile number.
  **⚠️ Standing obligation: any new table *or new PII column on `profiles`* must be added to this route's purge/anonymize list (and any new storage bucket to its cleanup list).** Same class of must-not-be-forgotten rule as the RLS note below — nothing enforces it automatically, and a table missed here silently keeps a deleted user's PII forever. When adding one, decide explicitly which bucket it falls in: delete (nobody else depends on it), anonymize in place (a counterparty row or an FK with no `on delete` clause points at it), or leave untouched (it's the counterparty's own history).
- **Security model** (004, extended in 012/013, **actually enforced since 040**): explicit per-table grants, column-level protection (no self-granting `is_verified`, immutable booking amounts) — **this was aspirational until migration 040; 004's column grants were additive on top of a table-level grant that overrode them, see the ⚠️ entry immediately below** —, promo codes readable only via `validate_promo_code()` RPC, storage buckets with mime/size limits and `<uid>/…` folder-scoped writes, security headers in `next.config.ts`, `safeRedirectPath()` on all `?next=` redirects. **`src/lib/listings.ts`'s `LISTING_COLUMNS`/`HOST_SELECT` is an explicit column list, not `*`** — found and fixed while building the map feature: `select('*')` on the public listings read path was leaking `street_address` into the RSC payload of `/listings/[id]`, `/hosts/[id]`, and search/home, before any booking existed. Any new listings query must use `LISTING_COLUMNS` (or extend it deliberately) rather than reaching for `*`. Verified live: created a listing with a real street address, confirmed it never appears in the rendered page HTML.

  **⚠️ Resolved by migration 040 (2026-09-02) — two table-level write holes, both proven live before the fix and both proven closed after.** Keeping the proof record here because it is the clearest worked example of how this project's grant behaviour actually differs from what its own migrations read like.
  - **Hole A — booking amounts were client-mutable.** Signed in as the demo renter with nothing but the public anon key: `create_booking` produced a legitimate booking at `total_amount` ₱2,490, then `PATCH /rest/v1/bookings?id=eq.<own booking>` with `{"total_amount": 1}` returned **HTTP 200 and the stored value actually became 1**. That completes into real money lost, because `src/app/api/payments/checkout/route.ts` prices the PayMongo intent as `booking.total_amount * 100` read back from the stored row — book at the right price, edit the price down, pay ₱1 on live keys. `create_booking`'s server-side pricing was being computed correctly and then simply overwritten afterwards.
  - **Hole B — `profiles.is_verified` was self-writable.** The same session could `PATCH` its own row's `is_verified` and the value changed (HTTP 204, verified changed, then restored). That made migration 037's verification gate decorative: self-verify, then self-publish (037's `block_self_publish()` guards `is_draft`, not `is_verified`), and wear the "Verified Host" badge with no admin ever reviewing an ID. `host_rating`, `host_review_count` and `response_time_hours` were self-writable the same way — forged ratings on listing cards, search and host profiles.
  - **Root cause, shared:** in Postgres a **table-level** UPDATE privilege satisfies a write to *any* column, so a column-level grant list is meaningless while the table-level grant is still held — it only ever adds, never narrows. This project's documented blanket bootstrap grant (see the ⚠️ grant-audit note below) hands `anon`/`authenticated` table-level UPDATE on essentially everything, and 004's `grant update (...)` statements for `bookings`/`profiles` (plus the later additive grants in 010/025/028) never `revoke` it first. `004_security_hardening.sql:127` already does it correctly for `reviews` — revoke, then grant specific columns — and `bookings`/`profiles` were simply never given the same treatment. 004's own header comment ("bookings: amounts + payment fields are insert-once") described an intent the database never enforced.
  - **Fix — `040_revoke_table_level_writes.sql`:** `revoke update on public.bookings from authenticated, anon` + `grant update (status, host_notes, renter_notes)`; `revoke update on public.profiles from authenticated, anon` + `grant update` on exactly the 11 columns the app legitimately writes (`full_name, avatar_url, is_host, bio, city, qr_payment_url, qr_payment_label, notify_new_booking, notify_messages, notify_reminders, notify_promos` — call sites `useProfile.ts` update/uploadAvatar/uploadQrCode/removeQrCode and `ListingWizard.tsx:165`); plus `revoke insert on public.bookings from anon`, the half 039 missed (039 revoked only from `authenticated`; `anon` was separately proven to still hold the grant because its INSERT was rejected by RLS rather than by a privilege check). `bookings.status` is in the list because `POST /api/bookings/[id]/respond` performs host accept/decline and renter cancel with the **user's** cookie session, not the admin client — who may make which transition is still decided by RLS + the `enforce_booking_transition` trigger.
  - **Verified live after applying, with real signed-in demo sessions on the anon key (never the service key, which bypasses all of this):** the exact `total_amount` PATCH now returns `permission denied for table bookings`, as do `rental_fee`/`service_fee`/`security_deposit`/`payment_status`; `is_verified`/`host_rating`/`host_review_count`/`response_time_hours` now return `permission denied for table profiles`; anon INSERT on `bookings` and anon UPDATE on `profiles` are now privilege-denied rather than RLS-denied. Every legitimate path was re-exercised and still works: all three Settings profile fields, all four notification toggles, `avatar_url`, `qr_payment_url`+`qr_payment_label` (write/clear/restore), `is_host`, `host_notes`/`renter_notes`, host confirm → host cancel → renter cancel through the real `POST /api/bookings/[id]/respond` route (including the availability-block trigger firing and unfiring), and the security-definer RPCs `create_booking`, `mark_booking_paid`, `confirm_host_qr_payment`, `validate_promo_code` — all unaffected, since they execute as the function owner. **Any new non-user-editable column on `profiles` or `bookings` is now server/RPC-only by default; a new user-editable one must be added to 040's grant list or its Settings save will 403.**

  **⚠️ Critical finding (016/017, 2026-07-18): this Supabase project silently grants broad INSERT/UPDATE/DELETE to `anon` and `authenticated` on essentially every `public` table, independent of whatever a migration explicitly `grant`s.** Discovered because `verification_requests` — which migration 015 only ever `grant select, insert`'d — turned out to also have `authenticated` holding UPDATE (`has_table_privilege('authenticated', 'public.verification_requests', 'UPDATE')` → `true`). A full audit (017) confirmed the same pattern across nearly the whole schema, including `anon` itself. Migration 004's own comment ("New Supabase projects do not auto-expose tables... every grant below is deliberate") is **wrong for this project's actual state** — something outside this repo's migrations (project bootstrap, or a pre-migration-history manual setup step) already granted broadly.
  **Why nothing is currently exploitable:** RLS is enabled on every table (`003`, `012`, `015`), and every command without a matching, correctly-scoped policy is denied by RLS's own default (INSERT → explicit 42501 error; UPDATE/DELETE with no matching row → a "successful" response that silently changes 0 rows). Verified live for the exact case that surfaced this: an authenticated user's direct `PATCH` to approve their own `verification_requests` row returns 403 and the row is provably unchanged.
  **What this means going forward — non-negotiable for any new table:** `alter table ... enable row level security;` **must** be in the same migration that creates the table, and every command your app relies on being blocked needs either a real policy or to rely on RLS's default-deny (never assume "I didn't grant it" is sufficient). A new table without RLS enabled would be **fully world-writable** the moment it's created, regardless of what `grant` statements are or aren't written. Don't remove 016/017 — they're the only record of this and can be re-run (017 especially) as a standing audit after adding new tables.

  **The production-CSP gap noted above was closed in the final whole-branch-review fix wave (2026-09-02):** both real screens (Settings → Identity Verification and the host wizard's Step 6) were driven under `npm run build && npm start`, not `next dev`.   **Two records that didn't exist yet, added in the same fix wave:** (i) on browsers without WebAssembly SIMD (older iOS before 16.4, older Android WebViews — both common in this market), MediaPipe's resolver requests `vision_wasm_nosimd_internal.*`, which is not vendored here (only the SIMD pair lives in `public/models/`), so the loader 404s and the user gets a silent, non-blocking `degraded` pass. That's honest at the database layer — the row is flagged `detector_unavailable` — but invisible in the UI, and it must not be read later as a suspicious pattern; it just means an old phone. Deliberately not fixing this by vendoring the nosimd pair too — that's another ~11 MB for a fallback path. (ii) The vendored WASM/model files in `public/models/` were copied by hand from `@mediapipe/tasks-vision`'s published package, and there is no sync script or checksum tying them to the npm dependency version. A future `npm install` landing a newer `@mediapipe/tasks-vision` under a caret range could pair a newer JS bundle with the stale 1.0.1 binaries — a mismatch whose failure mode is not a build error but `createFromOptions` throwing at runtime, silently turning every submission thereafter into a `degraded` pass. The dependency is now pinned exactly (`"1.0.1"`, no `^`) specifically to prevent that drift; bumping it deliberately in the future must re-copy `public/models/` in the same change.
  **Stated plainly, because it would be easy to overclaim this: this is not a security control.** The check runs entirely client-side in the uploader's own browser, the `auto_check_failed`/`auto_check_detail` flag is client-supplied and trivially forgeable by anyone willing to call the insert directly, and the override checkbox lets any user bypass it after two tries with zero server-side friction. Its only job is to stop the *accidental* case this task was built for — someone uploading the wrong photo by mistake — and to leave a breadcrumb for the reviewer when it does trigger. The `/admin/verifications` human review remains the actual, and only, gate on `profiles.is_verified`.

## Implementation Notes for Agents

- **Currency**: Philippine Peso, `₱X,XXX/day` format. Ratings like ⭐4.98.
- **No scope creep**: camera gear and smartphones only — no drones, laptops, consoles, vehicles.
- **Primary color class**: `#003049` (used inline as `bg-[#003049]` etc. throughout).
- **Images**: Unsplash/Pexels placeholders in dev; real assets in production.
- **Server-side money**: never trust client-computed amounts — all pricing goes through `create_booking`; payment confirmation only via service role. Keep it that way for refunds/payouts.
- **E2E test pattern**: sign in a demo account via the auth REST API, forge the SSR cookie (`sb-<ref>-auth-token` = `base64-` + base64url(session JSON)), drive the API routes, clean up with the secret key.
- **Commits**: imperative summaries describing the wired feature (see `git log`); the working convention is one commit per wired feature slice.
