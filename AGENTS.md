# Rentivo — Project Guide for Agents

## Project Overview

**Rentivo** is a peer-to-peer marketplace exclusively for camera, smartphone, and lens rentals. It connects equipment owners ("hosts") with renters for photography, videography, travel, content creation, events, and short-term projects. Philippine market: ₱ pricing, GCash/Maya payments, cities like Manila, Cebu, Davao.

The project started from a Claude Design prototype (`Rentivo.html` — still the canonical visual reference) and is now a working full-stack app: Next.js frontend, hosted Supabase backend (auth, database, storage), and PayMongo payments.

## Architecture Notes

- **Auth**: Supabase cookie sessions via `@supabase/ssr`; `src/proxy.ts` guards `/dashboard`, `/host`, `/book`, `/messages`. Signup enforces password policy client + server; hosted project requires email confirmation. **Google OAuth is enabled and verified working (2026-07-19)** — configured entirely in dashboards, nothing in this repo: a Google Cloud OAuth web client (redirect URI `https://prfizruuqwvteqovuqco.supabase.co/auth/v1/callback`) plus the Supabase Google provider (Client ID/Secret) and `http://localhost:3000/auth/callback` in the redirect allow-list. The consent screen is published (In production, External — any Google account works; basic scopes, no Google verification needed). Supabase Site URL is the prod domain, and the allow-list covers `/auth/callback` + `/reset-password` on both localhost and prod (the Google-side redirect URI never changes per environment).
- **Data layer**: server components call `src/lib/listings.ts`; client pages use hooks (`useBookings`). Host joins use explicit FK hints (`profiles!listings_host_id_fkey`).
- **Booking lifecycle**: `create_booking` RPC is the *only* insert path (direct inserts revoked — see the 038/039 note below for a security regression that briefly reopened this, caught by review). It computes all amounts server-side (5% service fee on the rental only, promo discount on rental fee only, delivery fee added on top when the renter chooses delivery — see the pricing note below) and creates the booking `pending` + `unpaid`. `mark_booking_paid` (service-role only, idempotent) is the only path to `paid`; Instant Book flips to `confirmed`, which triggers availability blocking. Renters may cancel only pending bookings; host transitions are trigger-enforced (`pending→confirmed→active→completed`). Host accept/decline **and** renter cancel both go through `POST /api/bookings/[id]/respond` (not a direct client table update) — RLS + the trigger still decide who's allowed which transition, the route just adds a server context to refund from and email from afterward. **Delivery fee** (038): `listings.delivery_fee` is nullable (`null` = not offered, `0` = free, `>0` = flat fee); `bookings.delivery_fee` is `not null default 0`. `create_booking` reads the fee off the *locked* listing row (never a client parameter), rejects a delivery booking if the host doesn't offer it, and excludes the fee from the service-fee base — it's a pass-through to the host, not commission. `request_payout()` pays hosts `rental_fee + delivery_fee`. `src/lib/pricing.ts` mirrors this math client-side for the checkout UI.
- **Listing publication** (037): a new listing from an unverified host is forced to `is_draft = true` by a `before insert` trigger, and an unverified host is blocked by a `before update` trigger from flipping their own draft to published (the service role is exempt) — enforced in the database because `authenticated` holds `insert`/`update` on `listings` and a client-side gate would be bypassable. `review_verification_request()` auto-publishes a host's pending listings on approval, after setting `is_verified`. Every public read path (RLS, `searchListings`, `create_booking`, detail/host-profile queries, `increment_listing_view`) already excludes `is_draft` rows, so this reuses existing plumbing rather than adding new state.
- **Refunds** (`src/lib/refunds.ts`): `refundBooking()` runs on every cancellation of a paid booking, from `/api/bookings/[id]/respond` — no-ops (`refunded: true`) if there was nothing to refund, so callers never pre-check payment_status. It's non-fatal: a failed PayMongo refund never blocks the cancellation itself, it just leaves `payment_status` at `paid` for manual follow-up (never falsely marks `refunded`). `mark_booking_refunded` (014, service-role only, idempotent) is the only path to `payment_status='refunded'`, mirroring `mark_booking_paid`. **PayMongo refunds draw against the merchant's payout balance** — a fresh test-mode account has none, so refunds will fail with `"Refund amount is greater than the available payout amount"` until the account has processed enough live/test volume to have a balance; this is documented PayMongo behavior, not a bug here (verified live: the refund call correctly reaches PayMongo with the right payment id/amount and is correctly rejected, and the booking still cancels either way).
- **Payments**: `POST /api/payments/checkout` creates/reuses the booking, creates a PayMongo intent for the server-computed total, attaches the payment method (cards tokenized in-browser with the public key — card data never touches our server; e-wallets server-side), and returns `paid` or a redirect URL. `/book/complete` verifies the intent after GCash/Maya/3DS redirects; `POST /api/webhooks/paymongo` (`payment.paid`, HMAC-verified) is the production source of truth. No PayMongo keys → simulated payments (dev only, still requires `SUPABASE_SECRET_KEY`). **Card payment methods must include `billing.email`** (PayMongo API requirement discovered live — 400s without it); the card form auto-fills it from the signed-in user's account email rather than asking for it again.
- **Notifications**: written *only* by security-definer triggers on `bookings` (request/confirmed/cancelled/completed/paid) and `reviews` (received) — never inserted by clients, so RLS only needs to scope reads and `is_read` updates to the owning user. `useNotifications` subscribes via Realtime in code; powers the navbar bell badge and the dashboard page. That subscription was silently inert until 2026-09-03 — `notifications` was not a member of the `supabase_realtime` publication — and **is now working**, fixed by migration 057.
- **Messaging** (rewritten 2026-09-03 — a thread used to *be* a booking; it no longer is, see the Status entry below for the full migration record): a `conversations` table (049) is the first-class thread object. Every booking still gets exactly one conversation (backfilled once by 050, created going forward by an `after insert` trigger on `bookings`, 055), but a conversation can now also exist **before** any booking — a pre-booking inquiry, opened via `create_inquiry(listing_id, content)` (055/056) from the "Message Host" CTA on a listing page (`InquiryDialog.tsx`). `useThreads()` reads `conversations` directly (`.or(renter_id.eq…,host_id.eq…)`), not bookings; `isInquiry` is simply `booking_id === null`. `useConversation` subscribes per-**conversation**, not per-booking, and auto-marks incoming messages read while open — the subscription itself is wired correctly but does not currently deliver (see the "Realtime does not deliver" finding in the Status entry below); a message only appears to the other party on their next page load/reload, not live. "Message Host"/"Message" CTAs deep-link to `/dashboard/messages?conversation=<id>` (new) or `?booking=<id>` (kept for existing links/emails — resolved client-side by looking up the conversation whose `booking_id` matches, since a fresh booking's conversation has zero messages and `useThreads()` deliberately drops zero-message *booking* threads to avoid surfacing empty ones — an inquiry thread is kept even at zero messages beyond its own opening message, since `create_inquiry` always inserts one). Messages can carry one image (message-images public bucket, `<uid>/<uuid>.<ext>` paths, 10 MB, upload in `useConversation.send()` before insert). `messages.booking_id` **was dropped by migration 060 on 2026-09-04**, together with the `fill_conversation_from_booking()` shim trigger that used to derive it; a thread's booking now lives only on `conversations.booking_id`, and a message insert must carry `conversation_id` (an old-shape `{booking_id, …}` insert is rejected by PostgREST as an unknown column). Message content is capped at 4000 chars by a CHECK constraint (058) and `create_inquiry` raises a readable error above 1000 (the composer's own limit).
- **Analytics**: `listings.view_count` increments via the `increment_listing_view` RPC (security definer, callable by anon+authenticated) called from `ViewTracker` on the listing detail page — a plain counter, not a deduped events log.
- **Identity verification**: `verification_requests` table (015) — real uploads to the existing private `verification-docs` bucket, one row per submission. Review is a single `review_verification_request(request_id, approve, notes)` RPC (service-role only), driven through the `/admin/verifications` panel (see the admin-panel Status entry) rather than the SQL editor directly — approving flips `profiles.is_verified` **and**, since 037, auto-publishes that host's pending (`is_draft`) listings. Users can never self-approve (only `select`/`insert` granted, RLS has no update policy so any client-side status write is a no-op). Wired in two places: `Step6Verify` in the host wizard (files stay local `File` state until the wizard's final submit, matching how photos already work) and a standalone `VerificationCard` in Settings (uploads immediately) for renters or hosts checking/resubmitting outside the wizard. A host's listings stay hidden (`is_draft = true`) until this approval — see the listing-publication note above.
  Before the human `/admin` review, both upload tiles now run an on-device face check (`src/lib/id-validation.ts`, `validateIdDocument`/`validateSelfie`) — see the "ID/selfie upload validation" Status entry below for what this catches and, just as importantly, what it doesn't.
- **Transactional email** (`src/lib/email.ts`, Resend): `notifyBookingPaid()` fires from all three places a booking can become paid (checkout route's simulated + real-charge branches, `/book/complete`'s redirect-verification, and the webhook — each guarded so it only fires on the actual unpaid→paid transition) and sends the host a "new request/instant booking" email plus the renter a "confirmed" or "payment received, awaiting host" email depending on `is_instant_book`. `notifyBookingResponded()` fires from `POST /api/bookings/[id]/respond` for both confirm and cancel — cancellation is asymmetric by design: it notifies whichever party *didn't* initiate it (host declining → emails the renter; renter cancelling → emails the host), and the copy reflects whether the refund actually succeeded (`refundBooking()`'s result) rather than always claiming one will happen. No `RESEND_API_KEY` → each call no-ops with a console log instead of failing; verified live by checking those log lines against triggered flows.
- **Pickup map**: `PickupMap` (`src/components/listings/PickupMap.tsx`) renders an interactive Leaflet map + **Esri World Topo** tiles (since 2026-09-03; previously OpenStreetMap Mapnik — see the basemap Status entry), pinned at the listing's **city center** (`src/lib/ph-locations.ts`, a static PH city/province → lat-lng table — no geocoding API, no ongoing cost, no account needed anywhere). Deliberately coarse: matches the existing privacy copy ("exact pickup address is shared after your booking is confirmed"). Switched off Mapbox mid-build after their signup flow rejected the account twice (unrelated to this repo) — OSM/Leaflet needs zero signup, which is why it's the default here rather than a hosted static-maps API. Leaflet touches `window`/`document`, so `PickupMapLeaflet.tsx` is `next/dynamic`-imported with `ssr: false` from the (client) `PickupMap.tsx` wrapper — don't import it directly into a Server Component, and don't drop the `ssr:false` guard. Note `listings.latitude`/`longitude` columns exist in the schema (001) but are unused/always null — don't wire them into any public-facing map without a privacy review, since unlike the city lookup they could hold an exact address if ever populated by a future feature. The search page reuses the same Leaflet stack via SearchMap/SearchMapLeaflet (src/components/search/) — city-grouped markers over the filtered results, HTML-escaped popup content, same ssr:false dynamic-import rule. **Both maps take their tile URL/attribution from `src/lib/map-tiles.ts`** rather than each declaring its own `L.tileLayer(...)`; that host must stay in sync with `img-src` in next.config.ts's CSP or every tile is silently blocked and the map renders blank grey.
- **Payouts**: `payout_accounts` (one per host, replace-not-append) / `payout_requests` / `payout_items` (020) — same manual-admin-review shape as identity verification: hosts write only through `set_payout_account()`/`request_payout()` (security-definer RPCs scoped to `auth.uid()`), and every status transition (`verified`/`rejected`/`paid`/`failed`) is a `service_role`-only RPC run manually from the SQL editor. `request_payout()` itemizes exactly which completed+paid bookings a request covers into `payout_items`, so a booking can never be claimed by two payout requests at once, and a failed request's bookings automatically become eligible again; 021 rewrote it to compute the amount and itemization from a single CTE so both come from one atomic snapshot (the original two-SELECT version had a race window). No live PayMongo disbursement — money movement itself is manual, matching this project's existing "verify live, no automated bank transfer" posture.
- **Host commission billing** (061–063, 2026-09-04; spec `docs/superpowers/specs/2026-09-04-host-commission-billing-design.md`) — **deliberately temporary**, for the period in which QR Ph is the only PayMongo method PayMongo has actually activated (see the Payments blocker note above): a host-QR booking puts the renter's full payment, Rentivo's 5% `service_fee` included, straight into the host's own GCash/Maya wallet, so unlike every other payment method that fee is never collected at the point of sale. This ledger bills it back monthly instead. **Data model**: `host_bills` (one row per `(host_id, period)`, a **partial** unique index `where status <> 'void'` so a corrected voided bill's slot can be re-billed in the same period) / `host_bill_items` (one row per booking, `booking_id` unique across all bills so a booking is ever billed once) — both RLS-enabled, `revoke all` then `grant select` to `authenticated` only; hosts read their own rows, nobody writes directly. **Eligibility** (the one definition, inside `generate_host_bills`): `payment_method = 'host_qr'`, `payment_status = 'paid'`, `status <> 'cancelled'`, `paid_at >= POLICY_START` ('2026-09-05 00:00+08', Manila-anchored so a booking near midnight doesn't shift months), `service_fee > 0`, not already itemized — with **no lower bound** on `paid_at` within the period, so a booking marked paid after its own month was billed is picked up by a later run rather than lost, and a host's running unbilled sum only actually gets issued once it reaches PayMongo's ₱100 minimum charge (below that, the bookings stay un-itemized and roll forward into a later, larger bill — never silently forgiven). **Three RPCs, all `service_role`-only**: `generate_host_bills(p_period date)` (idempotent, `on conflict (host_id, period) where status <> 'void' do nothing`, also inserts a `bill_issued` notification per bill since 063 — kept out of 061 itself because Postgres forbids using a new enum value in the transaction that adds it, same reasoning as 027/036/042), `mark_host_bill_paid(p_bill_id, p_paymongo_ref)` (idempotent, mirrors `mark_booking_paid`), `void_host_bill(p_bill_id, p_reason, p_rebill boolean default true)` (admin's only correction/waiver tool — `p_rebill = true`, correction mode, releases the items so a rerun re-bills them, even within the same period; `p_rebill = false`, waiver mode for a bill settled outside the app, leaves the items attached so those bookings are never billed again; a paid bill can never be voided). `is_host_billing_delinquent(p_host_id)` is `security definer`, **anon + authenticated**-granted, `stable` — true when any bill is `issued` and past `due_at` (14-day grace) — same shape and reasoning as `is_host_suspended()` (046): the answer must never depend on what the caller can read from `host_bills` itself. **Enforcement is a `before insert` trigger on `bookings`** (`block_delinquent_host_qr`), never an edit to `create_booking` — that function's body has already been copied across migrations often enough to cause two of this repo's own documented security incidents (038/039, 040), so billing enforcement stays structurally separate from booking-amount logic. **Delivery**: `POST /api/cron/host-bills` (Vercel cron, 1st of the month, bearer `CRON_SECRET`) and `POST /api/admin/bills/run` (admin "Run now", clamped to a completed month — cannot bill the current or a future one) both call `generate_host_bills` for the previous month and await every resulting `notifyHostBillIssued()` email before responding (`maxDuration = 60` on both, since a slow send must not truncate the response). **Paying**: `POST /api/bills/[id]/pay` — cookie session, RLS-scoped to the host's own bill — reuses a still-usable existing PayMongo QR Ph intent rather than minting a fresh one on a repeat click (marks the bill paid directly if that intent already succeeded), otherwise creates one; the existing `POST /api/webhooks/paymongo` `payment.paid` branch matches the intent back to a bill by `paymongo_ref` (with a metadata-`host_bill_id` fallback for a stale intent) and calls `mark_host_bill_paid` — both RPCs idempotent, so a replayed webhook event is harmless. A payment that lands on a bill no longer `issued` (voided or already paid) is logged, not silently dropped, though nothing today reconciles it automatically — voiding a bill with an active payment QR still out is flagged to the admin in the void confirmation. **Account deletion gate**: a third eligibility check in `src/lib/account-deletion.ts` blocks (400) any user with an `issued` `host_bills` row, alongside the existing in-flight-booking and pending-payout-request gates; `host_bills`/`host_bill_items` are deliberately **left untouched** on deletion (not anonymized, not purged) — same reasoning as `payout_accounts`/`payout_requests`, a financial record that must survive the user row. **UI**: host `/dashboard/bills` (`useHostBills`, `BillPayModal` — QR Ph, 3s polling like the booking checkout QR) and admin `/admin/bills` (month-picker "Run billing", a `?status=` filtered table, `BillVoidAction` with a required reason and an optional waive checkbox, every void writing an `admin_actions` audit row since it forgives real money owed); `/admin` gains an **Overdue bills** overview card, `/admin/reports` gains **Billed**/**Bill Payments** figures — **Billed − Bill Payments is what hosts still owe, not Uncollected − Bill Payments**, since Uncollected also includes amounts that can never be billed at all (`test_skip` bookings, pre-`POLICY_START` bookings, any sub-₱100 balance still rolling forward). Policy copy lives at `/host-terms`, linked from the host wizard and Settings' QR payment card. **Three do-not rules, all load-bearing**: never edit `create_booking`'s body for this feature (the trigger exists precisely so nobody has to); `POLICY_START`/grace-period live in exactly two places (`061_host_bills.sql` and `src/lib/billing.ts`) and must be changed together; `host_bills`/`host_bill_items` get no client write grant, ever — every transition is one of the three RPCs above.
- **Account deletion** (`src/lib/account-deletion.ts` — the module, **not** the route): service-role only and deliberately *not* a hard delete — `bookings`/`reviews`/`messages` reference `profiles` without `on delete cascade` while `profiles.id → auth.users` *does* cascade, so a real auth delete would wipe the counterparty's history. As of 2026-09-02 the logic lives in that one module and has **two** callers — the self-service Settings Danger Zone (`src/app/api/account/delete/route.ts`) and the admin panel (`src/app/api/admin/users/[id]/delete/route.ts`) — which both run the identical gates and the identical deletion; an admin gets no override, because removing a host mid-rental would strand a real renter's paid booking (suspension is the escape hatch for that case). The module anonymizes `profiles` into a "Deleted User" tombstone, deactivates + de-addresses the host's `listings`, nulls `bookings.delivery_address`, scrubs `payout_accounts` in place (its FK from `payout_requests` has no `on delete` clause), deletes only the rows nobody else depends on (`verification_requests`, `notifications`, `wishlist`, `recently_viewed_listings`), and finally soft-deletes the auth user via `deleteUser(uid, true)` — which blocks login while keeping the `auth.users` row, so the cascade never fires. Three eligibility gates run first (400): any booking in `pending`/`confirmed`/`active`, any `pending` `payout_requests` row, and (2026-09-04, host commission billing) any `issued` `host_bills` row — deleting during any of these would strand an in-flight rental, real owed money, or a real commission bill the host still owes. `host_bills`/`host_bill_items` are deliberately **left untouched** by the deletion itself (not anonymized, not purged) — a financial record, same reasoning as `payout_accounts`/`payout_requests`. Storage cleanup (`avatars`, `verification-docs`, `payment-qr-codes`) runs *before* the row deletes, since `verification_requests` holds the only record of the doc paths, and is non-fatal (log-and-continue) so a storage hiccup never blocks the auth soft-delete; `message-images` is left alone on purpose, as those belong to the counterparty's retained conversation. The anonymize update also nulls `qr_payment_url`/`qr_payment_label` (028) — the label is the host's real name + mobile number. `suspended_at` (044) is deliberately **not** anonymized: it is a moderation flag about an account, not personal data about a person, and clearing it on deletion would quietly un-hide a suspended host's listings as a side effect of deleting them. `conversations` (pre-booking inquiries, 049–056) holds `renter_id`/`host_id` and is likewise deliberately **left untouched** — same reasoning as `messages`/`message-images`: an inquiry thread is the counterparty's retained history, not the deleting user's alone, and nothing exercises the clause-less FK today since deletion never hard-deletes `profiles`. Decision recorded in the module itself, not just here.
  **⚠️ Standing obligation: any new table *or new PII column on `profiles`* must be added to `src/lib/account-deletion.ts`'s purge/anonymize list (and any new storage bucket to its cleanup list).** That module exists precisely so this obligation has exactly one place to discharge — the reason the logic was extracted out of the route in the first place was that the admin panel needed the same behaviour, and a second copy would have meant two lists to remember. **Do not copy this logic into a third caller.** Same class of must-not-be-forgotten rule as the RLS note below — nothing enforces it automatically, and a table missed here silently keeps a deleted user's PII forever. When adding one, decide explicitly which bucket it falls in: delete (nobody else depends on it), anonymize in place (a counterparty row or an FK with no `on delete` clause points at it), or leave untouched (it's the counterparty's own history).
- **Security model** (004, extended in 012/013, **actually enforced since 040**): explicit per-table grants, column-level protection (no self-granting `is_verified`, immutable booking amounts) — **this was aspirational until migration 040; 004's column grants were additive on top of a table-level grant that overrode them, see the ⚠️ entry immediately below** —, promo codes readable only via `validate_promo_code()` RPC, storage buckets with mime/size limits and `<uid>/…` folder-scoped writes, security headers in `next.config.ts`, `safeRedirectPath()` on all `?next=` redirects. **`src/lib/listings.ts`'s `LISTING_COLUMNS`/`HOST_SELECT` is an explicit column list, not `*`** — found and fixed while building the map feature: `select('*')` on the public listings read path was leaking `street_address` into the RSC payload of `/listings/[id]`, `/hosts/[id]`, and search/home, before any booking existed. Any new listings query must use `LISTING_COLUMNS` (or extend it deliberately) rather than reaching for `*`. Verified live: created a listing with a real street address, confirmed it never appears in the rendered page HTML.

  **⚠️ Resolved by migration 040 (2026-09-02) — two table-level write holes, both proven live before the fix and both proven closed after.** Keeping the proof record here because it is the clearest worked example of how this project's grant behaviour actually differs from what its own migrations read like.
  - **Hole A — booking amounts were client-mutable.** Signed in as the demo renter with nothing but the public anon key: `create_booking` produced a legitimate booking at `total_amount` ₱2,490, then `PATCH /rest/v1/bookings?id=eq.<own booking>` with `{"total_amount": 1}` returned **HTTP 200 and the stored value actually became 1**. That completes into real money lost, because `src/app/api/payments/checkout/route.ts` prices the PayMongo intent as `booking.total_amount * 100` read back from the stored row — book at the right price, edit the price down, pay ₱1 on live keys. `create_booking`'s server-side pricing was being computed correctly and then simply overwritten afterwards.
  - **Hole B — `profiles.is_verified` was self-writable.** The same session could `PATCH` its own row's `is_verified` and the value changed (HTTP 204, verified changed, then restored). That made migration 037's verification gate decorative: self-verify, then self-publish (037's `block_self_publish()` guards `is_draft`, not `is_verified`), and wear the "Verified Host" badge with no admin ever reviewing an ID. `host_rating`, `host_review_count` and `response_time_hours` were self-writable the same way — forged ratings on listing cards, search and host profiles.
  - **Root cause, shared:** in Postgres a **table-level** UPDATE privilege satisfies a write to *any* column, so a column-level grant list is meaningless while the table-level grant is still held — it only ever adds, never narrows. This project's documented blanket bootstrap grant (see the ⚠️ grant-audit note below) hands `anon`/`authenticated` table-level UPDATE on essentially everything, and 004's `grant update (...)` statements for `bookings`/`profiles` (plus the later additive grants in 010/025/028) never `revoke` it first. `004_security_hardening.sql:127` already does it correctly for `reviews` — revoke, then grant specific columns — and `bookings`/`profiles` were simply never given the same treatment. 004's own header comment ("bookings: amounts + payment fields are insert-once") described an intent the database never enforced.
  - **Fix — `040_revoke_table_level_writes.sql`:** `revoke update on public.bookings from authenticated, anon` + `grant update (status, host_notes, renter_notes)`; `revoke update on public.profiles from authenticated, anon` + `grant update` on exactly the 11 columns the app legitimately writes (`full_name, avatar_url, is_host, bio, city, qr_payment_url, qr_payment_label, notify_new_booking, notify_messages, notify_reminders, notify_promos` — call sites `useProfile.ts` update/uploadAvatar/uploadQrCode/removeQrCode and `ListingWizard.tsx:165`); plus `revoke insert on public.bookings from anon`, the half 039 missed (039 revoked only from `authenticated`; `anon` was separately proven to still hold the grant because its INSERT was rejected by RLS rather than by a privilege check). `bookings.status` is in the list because `POST /api/bookings/[id]/respond` performs host accept/decline and renter cancel with the **user's** cookie session, not the admin client — who may make which transition is still decided by RLS + the `enforce_booking_transition` trigger.
  - **Verified live after applying, with real signed-in demo sessions on the anon key (never the service key, which bypasses all of this):** the exact `total_amount` PATCH now returns `permission denied for table bookings`, as do `rental_fee`/`service_fee`/`security_deposit`/`payment_status`; `is_verified`/`host_rating`/`host_review_count`/`response_time_hours` now return `permission denied for table profiles`; anon INSERT on `bookings` and anon UPDATE on `profiles` are now privilege-denied rather than RLS-denied. Every legitimate path was re-exercised and still works: all three Settings profile fields, all four notification toggles, `avatar_url`, `qr_payment_url`+`qr_payment_label` (write/clear/restore), `is_host`, `host_notes`/`renter_notes`, host confirm → host cancel → renter cancel through the real `POST /api/bookings/[id]/respond` route (including the availability-block trigger firing and unfiring), and the security-definer RPCs `create_booking`, `mark_booking_paid`, `confirm_host_qr_payment`, `validate_promo_code` — all unaffected, since they execute as the function owner. **Any new non-user-editable column on `profiles` or `bookings` is now server/RPC-only by default; a new user-editable one must be added to 040's grant list or its Settings save will 403.** Since 059 the same holds for *reading* `profiles`: a new column is private by default, and one that public pages or `PROFILE_COLUMNS` need must be added to 059's `grant select (...)` list or every storefront embed that names it will 403.

  **⚠️ Critical finding (016/017, 2026-07-18): this Supabase project silently grants broad INSERT/UPDATE/DELETE to `anon` and `authenticated` on essentially every `public` table, independent of whatever a migration explicitly `grant`s.** Discovered because `verification_requests` — which migration 015 only ever `grant select, insert`'d — turned out to also have `authenticated` holding UPDATE (`has_table_privilege('authenticated', 'public.verification_requests', 'UPDATE')` → `true`). A full audit (017) confirmed the same pattern across nearly the whole schema, including `anon` itself. Migration 004's own comment ("New Supabase projects do not auto-expose tables... every grant below is deliberate") is **wrong for this project's actual state** — something outside this repo's migrations (project bootstrap, or a pre-migration-history manual setup step) already granted broadly.
  **Why nothing is currently exploitable:** RLS is enabled on every table (`003`, `012`, `015`), and every command without a matching, correctly-scoped policy is denied by RLS's own default (INSERT → explicit 42501 error; UPDATE/DELETE with no matching row → a "successful" response that silently changes 0 rows). Verified live for the exact case that surfaced this: an authenticated user's direct `PATCH` to approve their own `verification_requests` row returns 403 and the row is provably unchanged.
  **What this means going forward — non-negotiable for any new table:** `alter table ... enable row level security;` **must** be in the same migration that creates the table, and every command your app relies on being blocked needs either a real policy or to rely on RLS's default-deny (never assume "I didn't grant it" is sufficient). A new table without RLS enabled would be **fully world-writable** the moment it's created, regardless of what `grant` statements are or aren't written. Don't remove 016/017 — they're the only record of this and can be re-run (017 especially) as a standing audit after adding new tables.

This closes the layer-1 hole: **an already-issued JWT stays valid for up to an hour after the ban**, so without this a suspended host keeps full use of their dashboard for the remainder of the access-token lifetime. A hit redirects to `/login?suspended=1` and deletes the auth cookies, so the next request is a clean signed-out state rather than a loop through the same check. Deliberately scoped to protected prefixes: those pages already query the database, so the read is free there, while public browsing — the overwhelming majority of requests — stays query-free. **This check fails OPEN on a query error**: it tests `profile?.suspended_at`, so a failed or errored read is indistinguishable from "not suspended" and the request proceeds. That is the right trade for availability — a database hiccup must not lock every signed-in user out of their dashboard — and layer 1's GoTrue ban still blocks *new* logins regardless. But it means a database problem silently disables this layer with nothing logged, so do not read "the middleware would have caught it" as a guarantee. Layer 3 (the database itself) is the only layer that cannot fail open this way.
  3. **The database**, which is what actually removes the gear from the marketplace: `listings: public read active` gains `and not public.is_host_suspended(host_id)` (045, rewritten in 046 — see below), and `increment_listing_view` and `create_booking` gained the equivalent inline guard.

  **Six app read paths had to be given the same predicate**, because `authenticated` holds broad grants here and every public read path must agree rather than trusting one of them: `getFeaturedListings`, `getPopularListings`, `getBundles`, `getActiveListingCount`, `searchListings` (`src/lib/listings.ts`, each switched to an `!inner` host join so `host.suspended_at` is filterable) and `getHostProfile` (`src/lib/hosts.ts`, `.is('suspended_at', null)` — a suspended host's public profile 404s). **`getListing` deliberately does NOT get an app-level filter and relies on RLS alone** — the RLS policy already excludes a suspended host's listing, so a mirrored filter would be a second thing to keep in sync for no added coverage. **This file previously gave the wrong reason** — it said `getListing` "has no host join to filter on", which is false: `src/lib/listings.ts:124` selects `HOST_SELECT`, which *is* a host join. The real distinction is that `HOST_SELECT`'s embed is a **plain** one while the five mirrored call sites use `HOST_SELECT_INNER`. A PostgREST filter on an embedded table only restricts the parent row when the embed is `!inner`; against a plain embed it filters what comes back *inside* the embed and the parent row still returns. So adding `.is('host.suspended_at', null)` to `getListing` as written would not have filtered anything — it would have looked like a guard and done nothing. That `!inner`-vs-plain trap is the whole reason the five mirrored paths were switched to `HOST_SELECT_INNER`; do not "tidy" any of them back to a plain embed. The five mirrored filters are not the enforcement — RLS is — they exist so the rule is visible at the call site instead of only in a migration.

  **⚠️ Migration 046's `is_host_suspended(uuid)` `security definer` helper is the most important line in this workstream, and the reason for it is not obvious.** 045 wrote the RLS predicate as an inline `not exists (select 1 from profiles ...)` subquery. **A subquery inside a policy's `USING` clause runs with the *invoker's* privileges**, so `profiles`' own RLS applies to it. That is correct *today* only because `profiles` carries `public read using (true)`. The moment that policy is narrowed — which `TODO.md` explicitly contemplated, for the `qr_payment_label` exposure — the subquery would return zero rows for `anon`, `not exists` would evaluate to true, and **every suspended host's listings would silently return to the marketplace with no error raised anywhere**. It fails *open*, and it would fail open as a side effect of an unrelated security improvement in a different file. Routing the check through a `security definer` function makes the answer independent of the caller's view of `profiles`, so the failure mode becomes "cannot happen" rather than "depends on a policy someone else may edit". `increment_listing_view` and `create_booking` were deliberately **not** converted: both are already `security definer`, so their inline subqueries execute as the function owner and the failure mode does not apply — and converting `create_booking` would mean reproducing its body a second time, and every such reproduction is a chance to disturb the amounts logic that has already caused two security incidents in this repo. The inconsistency is the cheaper risk.

  **Six money paths are now closed to a suspended host** — suspension that hides gear but still lets money move is not suspension: `create_booking` (045), `request_payout` (046), `confirm_host_qr_payment` (047), `set_payout_account` (048), `/api/payments/checkout`'s **booking-reuse branch** and `GET /api/bookings/[id]/qr` (both app code). **This paragraph said "Four" and read as exhaustive; it was not** — the final whole-branch review found two more, and the honest lesson is that "how many are there" was never derived from a list of every place money can move, only from the places someone had thought of. Treat the count as the current tally, not a proof of completeness: anything new that moves money, reveals payment details, or changes where money lands needs its own guard, and there is no mechanism that will catch a missing one for you.
  The two the review added:
  - **`GET /api/bookings/[id]/qr` — the one a party-scoped route hides.** Every other guarded path is exercised by the suspended host themselves, so the middleware check or an `auth.uid()` guard catches it. This route is scoped to the booking's two *parties*, and the party who calls it is the **renter**, who is not suspended — so middleware never fires. Without the guard a renter could open a suspended host's personal GCash QR from `/dashboard/rentals` and pay them off-platform for a booking that can then never be marked paid (047 closed `confirm_host_qr_payment`), losing real money on a rental that cannot happen, with no refund possible because Rentivo never held it. The response also carries `qr_payment_label` — the host's real name and mobile number. The guard reuses the route's own `Booking not found.` 404 rather than a distinct message, matching the checkout route's choice. The renter-facing affordance on `/dashboard/rentals` is withheld too, via a client-side `is_host_suspended` call (that RPC is already granted to `anon`, so asking it discloses nothing new; `suspended_at` is deliberately **not** in `PROFILE_COLUMNS`), with copy telling the renter not to pay the host directly.
  - **`set_payout_account` (048) — redirecting where money lands, not whether it leaves.** `request_payout` was guarded on the reasoning that suspension must stop money *leaving* the platform. `set_payout_account` uses `on conflict (user_id) do update` (020:110), so it rewrites the **same** `payout_accounts` row that an existing `payout_requests.payout_account_id` already points at. Inside the ≤1h access-token window a suspended host could therefore change the account number underneath a still-`pending` request, redirecting where the admin sends real money at Mark Paid time — indistinguishable in kind from the guarded case. It does **not** retroactively protect a row rewritten *before* the suspension; the defence for that stays the suspended-host badge on `/admin/payouts` plus the manual, service-role-only status transitions.

  The `/api/payments/checkout` booking-reuse branch is the other non-obvious one: a booking created *before* the suspension sits there `unpaid`, and `create_booking`'s guard only covers the branch that creates a *new* row, so without the added `is_host_suspended` call the reuse path would happily take real money for a host who is off the marketplace. Its error message deliberately duplicates the adjacent "Booking not found or already paid." rather than saying why — a renter has no business learning the moderation state of a stranger's account. The two RPCs a *suspended host themselves* calls (`request_payout`, `confirm_host_qr_payment`) do name the reason, since the caller already knows their own state.
  **`mark_booking_paid` is deliberately left unguarded, and that is a decision rather than an oversight.** It is service-role-only and reachable from the PayMongo webhook and `/book/complete`; both callers now refuse to *start* a charge for a suspended host, so the only way to reach it is a payment already in flight. Guarding it would strand a renter mid-redirect whose money has genuinely already moved — leaving them charged with no booking. Failing to record a payment that really happened is worse than recording one for a host who is suspended.

  **`profiles.suspension_reason` was added in 044 and dropped again in 047 — do not re-add it.** `profiles` carries `public read using (true)`, so `anon` could select admin-authored free text *about a user* straight off the table via a raw PostgREST call (verified before writing the migration). That is the worst possible shape of data to leave on a publicly readable row. A column-level `revoke` was **not** viable: this project's documented finding (the ⚠️ 040 write-up below) is that a table-level grant satisfies a read or write to *any* column, so column-level grants only ever add and never narrow; closing it properly would mean revoking table-level SELECT on `profiles`, which every public read path depends on. The column was dropped rather than defended because it was **redundant** — the reason now lives in exactly two places, `admin_actions.detail` (service-role only) and the suspension email, and nothing needed it on the profile row. `suspended_at` stays: it is the flag every read path checks and it discloses only a boolean-equivalent fact about a listing that has already left the marketplace. Zero rows held a non-null reason at drop time, so no data was destroyed.

  **`profiles_suspended_idx` (044, a partial index on `suspended_at is not null`) is NOT load-bearing for the read paths.** Every suspension read predicate asks the *inverse* question — "is this one host suspended?", via `is_host_suspended(host_id)` or a `not exists` on a single `profiles.id` — so the planner uses the `profiles` primary key, not this index. The index serves the admin-side "list the suspended accounts" direction. Do not cite it as the reason the marketplace read paths stay fast, and do not assume dropping it would slow them down.

  **`admin_actions` (044) has RLS enabled with no policies at all, by design.** It is read and written only by the service-role client, which bypasses RLS, so default-deny is exactly right; the accompanying `revoke all ... from anon, authenticated` is a second mechanism, not the one that makes it safe. `target_user_id` deliberately carries **no foreign key** — a delete action's whole point is that the target may stop being a normal row, and the audit log must never become the reason a future cleanup can't run. **It logs attempts, not outcomes**, and reading it as a list of completed actions will mislead: the delete route audits *before* acting (afterwards the profile is anonymized and the auth address gone, so the captured `{ email, full_name }` would be unrecoverable) and treats a failed audit insert as **fatal**, aborting the deletion; and one logical suspension can produce **two** rows, because the ban-failure path writes a `{ ban_failed: true }` row and the admin's retry then writes a normal one. The suspend/unsuspend routes treat a failed audit as non-fatal by contrast, since the action has already fully applied and a failed log must not undo it.

  **Suspend-route ordering is deliberate**: the profile flag is set *before* the GoTrue ban, so a failure between them leaves the account reading as suspended with its listings already hidden — the safe direction to fail. The reverse would leave a banned account still showing as active in the panel. The "already suspended" guard therefore tests **both halves** (`suspended_at` set *and* `banned_until` in the future) rather than `suspended_at` alone, so a half-applied suspension stays retryable instead of being permanently stranded by its own guard. The route also fails **closed** on a GoTrue read error — `{ user: null, error }` would make `isAdminEmail(undefined)` false and let an admin be suspended — and refuses to suspend or delete any allowlisted admin, including the acting admin themselves, since locking out the only admin would leave nobody able to undo it.

  **Account deletion was extracted into `src/lib/account-deletion.ts`** so the admin route and the self-service Settings route run byte-identical gates and deletion — see the architecture note above, which now points the standing purge-list obligation at that module rather than at the route. An admin gets no override on the two eligibility gates.

  **Commission definitions, recorded verbatim because the distinction is a property of the business model and not a bug to fix:**
  - **Earned** — total `service_fee` on every paid, non-cancelled booking, regardless of payment method.
  - **Collected** — earned via `card`, `gcash`, `maya` or `qrph`: the methods Rentivo's **own** PayMongo account processes, so the fee actually reaches Rentivo.
  - **Uncollected** — earned on `host_qr` and `test_skip` bookings. **These earn a service fee that is never collected**: with `host_qr` the renter pays the host's personal GCash/Maya QR directly and Rentivo never touches the money; `test_skip` is the pre-launch no-charge testing method. The card is amber, not red — this is a fact about how the platform takes payment, not an error.
  `PAYMONGO_METHODS` is written as an explicit **allowlist, never a negation**: `payment_method` is nullable and the enum still carries unused `apple_pay`/`google_pay` values, so a future method must be deliberately classified rather than silently counted as revenue. Live figures at time of writing (8 paid non-cancelled bookings): **earned ₱3,168 / collected ₱2,208 / uncollected ₱960**.
  The reports page's **Revenue** column is `total_amount − security_deposit`, not `total_amount`: at this dataset's current mix **60.6% of `total_amount` is refundable security deposit** Rentivo is merely holding, so a column labelled with the full total would badly mislead anyone skimming the page. The one money column on that page that is still deposit-*inclusive* is Rentals In Flight's, and it is labelled **"Booking Total"** with a caption saying so.

- [x] Pre-booking inquiries (2026-09-03, migrations 049–056; the column drop landed as 060 on 2026-09-04): closed the gap the previous entry's report surfaced ("message host is not working," because a message thread used to *be* a booking, so there was nowhere to put a message sent before one existed). Built via spec → plan → 5 tasks (conversations table → backfill+shim → messages RLS pivot → create_inquiry RPC → hooks/email/UI), each with its own fix round, plus this task as a whole-system verification pass on top.
  **The model.** `conversations` (049) is now the first-class thread object: `(id, listing_id, renter_id, host_id, booking_id nullable, created_at, last_message_at)`. `booking_id null` = an open inquiry; set = attached to a booking. `messages` gained `conversation_id` (051, `not null`, `on delete cascade`) and RLS pivots on it (053) instead of on `booking_id` — a bookingless conversation was structurally unreadable under the old policy (it joined through `bookings`), which is the actual reason a pre-booking thread needed a schema change and not just a UI change.
  **The partial unique index is load-bearing, not decorative.** `conversations_open_inquiry_key` is `unique (listing_id, renter_id) where booking_id is null` — PARTIAL specifically because an unconditional `unique(listing_id, renter_id)` would fail against data that already existed: **4 of the database's bookings are repeat rentals, across 3 distinct `(listing, renter)` pairs** (one renter booked one listing 3 times, and two other listing/renter pairs twice each — confirmed by `group by listing_id, renter_id having count(*) > 1` against the live database). Every one of those needs its own conversation; the partial form exempts attached rows so only *open* inquiries are capped at one per pair, and a booking's own conversation is never blocked by an earlier one that already got consumed.
  **`on delete cascade` on `conversations.booking_id`, deliberately, not `set null`.** `messages.booking_id` already cascaded before this work — deleting a booking already destroyed its messages. `set null` would have silently changed that (messages would survive as an orphaned, unbounded inquiry) and could additionally violate the partial unique index by turning a just-deleted booking's attached conversation back into an "open" one that collides with a genuinely open inquiry for the same pair. Cascade preserves the pre-existing semantics exactly.
  **Attaching an inquiry to a new booking is a trigger (055's `attach_conversation_to_booking()`, `after insert on bookings`), not an edit to `create_booking()`.** That function's body has already been reproduced across several migrations, and each reproduction has been a chance to disturb the amounts logic — the exact class of mistake that produced two of this repo's own documented security incidents (038/039, 040). The trigger UPDATEs an existing open conversation for the same `(listing_id, renter_id)` if one exists, and INSERTs a fresh one (with the booking already attached) if not — the second, repeat-rental case is not incidental coverage: the partial unique index guarantees at most one open inquiry per pair, so a *second* booking of the same listing by the same renter necessarily finds the first UPDATE matching zero rows and must fall through to the INSERT branch to succeed at all. Task 10's verification exercises this directly (a same-listing, same-renter booking made twice in one run; the second gets a distinct conversation with correctly matching `listing_id`/`renter_id`/`host_id`) — **this branch is not untested**, and a document that says otherwise is wrong.
  **The 10-conversations-per-24h cap on `create_inquiry` (055/056) is a guess, not a measurement.** There is no traffic data behind the number — it exists to bound spam/abuse at all, and is deliberately one named constant (`v_max_per_day`) so changing it later is a one-line edit, not a body rewrite.
  **`messages.booking_id` — DROPPED by 060 on 2026-09-04; the paragraph below describes the state between 054 and 060.** It still existed, was still populated, and the app no longer read it for anything. A `before insert` trigger (`fill_conversation_from_booking()`, 051/052/054) derives `conversation_id` from a client-supplied `booking_id` for any caller still using the pre-migration insert shape, and — the direction that actually matters for security, not just compatibility — always overwrites `booking_id` FROM the resolved `conversation_id` afterward, so a client can never make the two disagree. Dropping the column outright was deferred to an optional migration (numbered 057 when this was written) and **has now been applied as 060**.
  **Three security findings, found and fixed during this workstream — the exact class of thing this file exists to preserve:**
  - `messages` carried a **table-level UPDATE grant** to `anon`/`authenticated`, which made migration 013's `grant update (is_read)` decorative — a table-level grant satisfies a write to *any* column regardless of what a column-level grant list says, so a participant could rewrite the *other* party's message content or `sender_id`, not just their own read receipt. Closed in 053 by `revoke update on messages from anon, authenticated` followed by `grant update (is_read) to authenticated` — the identical revoke-then-grant shape migration 040 already established for `bookings`/`profiles`. Verified live pre-fix (a real tamper attempt against `content` succeeded before the revoke) and post-fix (the identical attempt now returns `permission denied for table messages`).
  - **The first version of 053's INSERT policy validated conversation membership but not `booking_id`.** Since 004 grants table-level INSERT on `messages` with no column restriction, a participant could POST into their own real conversation while setting `booking_id` to an unrelated stranger's booking. RLS's own read path correctly hides such a row from both real parties (it isn't in their conversation) — which is exactly why this was easy to miss. The actual exposure: `notifyNewMessage()` runs on the **admin client** and resolves its email recipient from `message.booking_id`, bypassing RLS entirely, so a crafted insert could make Rentivo email attacker-supplied text to an unrelated stranger from `noreply@rentivo.live`. Closed in 054 by having the same `before insert` trigger that fills `conversation_id` **always** overwrite `booking_id` FROM the conversation afterward, never trusting the client-sent value — the same fix that keeps the eventual column drop (060) safe to defer, since a lingering mismatch is now structurally impossible rather than merely untrusted.
  - **`conversations.last_message_at` was briefly set from client-supplied `messages.created_at`.** The `after insert` trigger that bumps thread ordering (`touch_conversation_last_message()`) originally used `new.created_at`, and since `messages.created_at` has no column-level write restriction, a participant could insert a message with a future timestamp and pin their own conversation to the top of both inboxes indefinitely.
