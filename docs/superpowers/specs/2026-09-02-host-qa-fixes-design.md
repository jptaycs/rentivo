## 1. "Digital Camera" category

### Problem

`equipment_category` (migration `001`) offers `mirrorless | dslr | cinema | smartphone | lens | bundle`. A host listing a Canon G7X Mark III — a compact digital camera — has no category that fits, and shoehorned it into an existing one.

### Design

**Migration `036_add_digital_camera_category.sql`** — enum value only, nothing else:

```sql
alter type equipment_category add value 'digital';
```

This must be its own migration. Postgres does not permit *using* a newly added enum value in the same transaction that adds it — the same reason `027` isolated `'host_qr'`.

**Application wiring** (no other DB change):

- `src/types/index.ts` — add `'digital'` to the category union.
- `src/components/host/Step2Details.tsx` — `CATEGORIES` gains `{ value: 'digital', label: 'Digital Camera' }`, positioned after DSLR. Subtitle copy: *Compact & point-and-shoot*.
- `src/components/search/FilterSidebar.tsx` — add the category checkbox.
- `src/app/(main)/dashboard/listings/[id]/edit/page.tsx` — add to the category list.
- `src/lib/mock-data.ts` — type compatibility only; no new mock listing required.

**Deliberately unchanged:** `CategoryCards.tsx` and `HeroSearch.tsx` keep their four existing entries. Digital cameras fold under the existing "Cameras" browse path rather than adding a fifth home-page card.

**Scope note:** `AGENTS.md` documents the equipment-category list as a hard scope boundary ("do not add others"). That list is amended to include Digital Cameras as part of this work, so the addition reads as a deliberate product decision rather than scope creep.

## 2. Province coverage and map detection

### Problem

Two separate, drifting sources of location truth:

- `src/components/host/Step5Address.tsx` hardcodes its own 13-province array plus an `'Other'` escape hatch.
- `src/lib/ph-locations.ts` holds an unrelated table of 19 city and 12 province coordinates.

Nothing keeps them in sync. A host outside those 13 provinces must pick `'Other'`, and `getCityCoordinates(city, 'Other')` matches neither table and falls through to the Manila default.

**Confirmed in production:** listing `924ca665…` is `city: "NAGA CITY CAMARINES SUR", province: "Other"` and pins in Manila.

### Design

`src/lib/ph-locations.ts` becomes the single source of truth for Philippine locations.

- **`PROVINCE_COORDS`** — all 82 provinces, keyed by normalized lowercase name.
- **`CITY_COORDS`** — expanded from 19 to roughly 145 entries, covering the chartered cities.
- **`PH_PROVINCES`** — a new exported, sorted array of province display names. `Step5Address.tsx` imports this instead of maintaining its own list. The dropdown and the coordinate table then cannot disagree, which is the structural fix; a larger table alone would only postpone the same bug.

**Lookup order** in `getCityCoordinates(city, province)`:

1. Exact match on the normalized city key.
2. Match against known cities within the selected province (handles free-text input like `"NAGA CITY CAMARINES SUR"` where the host typed more than the city name).
3. Province center.
4. Manila.

Normalization strips case, surrounding whitespace, punctuation, and a trailing `"City"`.

**`'Other'` is removed from the dropdown** — redundant once all 82 provinces are present. The fallback chain still resolves `province: 'Other'` for the existing rows, so no historical data breaks.

**Coordinate accuracy.** The table is generated by cross-checking each province and city name against a public geocoder **at authoring time**, with the verified results baked into the file. No runtime API call, no new dependency, no account — preserving the deliberate zero-cost OSM/Leaflet posture. A one-off generation script is throwaway and is not committed as a runtime dependency.

**Blast radius:** `PickupMap` (listing detail) and `SearchMap` (search results) both call `getCityCoordinates`, so both are fixed by this change alone.

## 3. Duplicate listing on submit

### Problem

`ListingWizard.handleSubmit()` performs five sequential writes:

1. Upload each photo to `listing-images`
2. `insert` into `listings`
3. `insert` into `availability_blocks`
4. `update profiles.is_host`
5. Upload ID + selfie, `insert` into `verification_requests`

The listing insert is step 2 of 5. Any failure in steps 3–5 throws, surfaces an error banner, and leaves the wizard on step 6 — and the retry re-runs **all five steps from the top**, uploading fresh photos and inserting a second listing.

**Confirmed in production.** Two `Canon G7X Mark III` rows exist for host `c38111b3…`, created `16:36:37` and `16:36:54`, with *different* image URLs (proving a full re-run, not a double-click on one submit). The `verification_requests` row landed at `16:36:55` — only the second attempt completed.

### Design

Three changes to `src/components/host/ListingWizard.tsx`:

**Resume rather than restart.** Completed sub-steps are recorded in refs that survive a failed attempt:

- `uploadedImagesRef` — photo URLs already uploaded. A retry skips files already in the map.
- `listingIdRef` — set the moment the listing row is created. If it is already set, a retry **updates** that row instead of inserting a new one. This is the critical guarantee: once a listing exists, no retry can ever create a second.

**Late failures stop being fatal.** After step 2 succeeds, the listing exists and the host's work is saved. Failures in steps 3–5 no longer throw the host back into a retry loop; they land on the success screen with a specific, actionable warning, e.g. *"Listing created, but your ID upload failed — you can retry it in Settings."* This removes the condition that produced the duplicate in the first place.

**Double-submit guard.** A `submittingRef` closes the same-tick window where two rapid clicks both pass the `disabled={loading}` check before React re-renders.

**Pre-submit file validation.** Client-side type and size checks on the photo, ID, and selfie files before any upload starts, so a bucket-policy rejection surfaces as a clear message rather than a raw storage error mid-transaction.

### Data cleanup

Delete listing `924ca665-bcde-4039-af36-b92f65723d49` (the abandoned `16:36:37` attempt) and its three orphaned `listing-images` storage objects. No bookings reference it. The surviving row is `654bfee2-586d-4e18-9138-fcc48cc3fe07`.

## 4. Admin ID verification gate before publish

### Problem

A listing goes live the instant it is inserted, regardless of whether the host's identity has been verified. **Confirmed:** host `c38111b3…` is `is_verified: false` with a `pending` verification request, yet both their listings are `is_draft: false, is_active: true` and publicly searchable.

### Design

The wizard inserts into `listings` directly — there is no `create_listing` RPC — and `authenticated` holds `insert, update, delete` on the table (migration `004`). A client-side check would therefore be trivially bypassable. **Enforcement belongs in the database.**

This reuses the existing `is_draft` column rather than adding new state. Every public read path already excludes drafts: RLS policy `003`, `create_booking` (`035`), `searchListings`, the home/host-profile/detail queries, and `increment_listing_view` (`011`). Policy `"listings: host read own"` already lets a host see their own drafts, so My Listings keeps working with no query change.

**Migration `037_gate_listings_on_verification.sql`**, in this order:

1. **Verify the seed/demo hosts.** Four of nineteen hosts are unverified, two of them seed fixtures: Andrei Flores (`…012`, Google Pixel 9 Pro) and Lea Villanueva (`…004`, Sony 24-70mm), plus Demo User (`…0ff`). These are marketplace fixtures, not real unverified hosts. Set `is_verified = true` for them **before** the retroactive sweep below, or the storefront visibly empties out.

2. **`before insert` trigger on `listings`** — forces `new.is_draft = true` when the host's `profiles.is_verified` is false. Verified hosts publish instantly, exactly as today.

3. **`before update` trigger on `listings`** — blocks an unverified host from moving `is_draft` from `true` to `false`. Follows the `enforce_booking_transition` (`004`) precedent of returning early when `auth.uid() is null`, so the service role and security-definer admin paths are never blocked. Only the `is_draft` transition is guarded; `is_active` (pause/activate) and ordinary field edits are untouched.

4. **Extend `review_verification_request`** (authoritative body in `018`) so that approving an ID also flips that host's pending listings live in the same transaction:

   ```sql
   update public.listings set is_draft = false
   where host_id = v_request.user_id and is_draft = true;
   ```

   **Ordering matters inside this function:** set `profiles.is_verified = true` *first*, then publish the listings. The `before update` trigger early-returns for the service role so it would not block either order, but relying on that bypass rather than on the host genuinely being verified would make the function correct by accident.

   This is the auto-publish behavior chosen during design. The function stays `security definer` and `service_role`-only granted; the `/admin` panel remains its only caller.

5. **Retroactive sweep** — set `is_draft = true` for any currently live listing whose host is not verified. After step 1, this affects only the one genuine unverified host's listing.

**Host-facing UI:**

- `/dashboard/listings` shows a "Pending review" badge on `is_draft` listings.
- The wizard's success screen tells an unverified host their listing goes live once their ID is approved, instead of today's unconditional "Listing submitted!".

## 5. Delivery fee

### Problem

There is no delivery fee anywhere in the system: no column on `listings` or `bookings`, no term in `create_booking`, nothing in `src/lib/pricing.ts`. The checkout UI says *"Fee may apply"* and *"Delivery fee will be arranged directly with the host via messages."* This is net-new pricing, not a display bug.

### Design

Money is computed server-side from the listing row and never trusted from the client, consistent with every existing amount.

**Migration `038_delivery_fee.sql`:**

**Schema**

```sql
alter table public.listings add column delivery_fee integer check (delivery_fee >= 0);
alter table public.bookings add column delivery_fee integer not null default 0 check (delivery_fee >= 0);
```

`listings.delivery_fee` is **nullable on purpose**, and the three states are distinct:

| Value | Meaning | Checkout behavior |
|---|---|---|
| `null` | Host does not offer delivery | Delivery tile disabled |
| `0` | Free delivery | Tile shows "Free" |
| `> 0` | Flat fee | Tile shows the amount |

Without the nullable third state, "₱0" and "not offered" are indistinguishable.

`bookings.delivery_fee` is `not null default 0` so historical bookings keep honest, unchanged receipts — the same approach `035` took when discontinuing the protection fee.

**`create_booking`** — redefined from `035`'s authoritative body, with these changes only:

- New local `v_delivery integer := case when p_is_delivery then coalesce(v_listing.delivery_fee, 0) else 0 end;` — read from the locked listing row, never from a parameter.
- Reject a delivery booking against a listing that does not offer one: `if p_is_delivery and v_listing.delivery_fee is null then raise exception 'This host does not offer delivery.'; end if;` — mirroring the existing `host_qr` guard.
- `v_delivery` added to the `insert` column list and to `total_amount`.

Final total becomes:

```
v_rental - v_discount + v_service + v_protection + v_delivery + v_listing.security_deposit
```

**Service fee is unchanged** — still `round(v_rental * 0.05)`. The delivery fee is a pass-through to the host, not a commission base.

**`request_payout()`** — redefined from `033`'s authoritative body. Its eligible CTE currently sums `b.rental_fee` alone; it must sum `b.rental_fee + b.delivery_fee` in all three places (the CTE projection, the `sum()` in the request insert and its `having`, and the `payout_items` amount). Missing this would silently make the host absorb every delivery cost.

**Grants** — `004`'s column-level `grant insert (...) on public.bookings` list extends with `delivery_fee`.

**Application wiring:**

- `src/lib/pricing.ts` — `PricedListing` gains `delivery_fee: number | null`; `calcPricing()` takes an `isDelivery` flag and includes the fee in its total, mirroring the RPC exactly.
- `src/lib/listing-columns.ts` — `delivery_fee` added to `LISTING_COLUMNS`. (Required: the explicit allowlist means a new column is invisible to every read path until listed. See the `street_address` and `qr_payment_label` incidents.)
- `src/types/index.ts` — `Listing.delivery_fee`, `Booking.delivery_fee`.
- `src/components/host/Step3Pricing.tsx` — an optional delivery-fee input, with "leave blank if you don't offer delivery" copy that makes the null state explicit.
- `src/app/(main)/dashboard/listings/[id]/edit/page.tsx` — same field.
- `src/components/booking/Step2Pickup.tsx` — the Delivery tile shows the real fee, "Free", or a disabled "Not offered by this host" state, replacing today's "Fee may apply" / "arranged via messages" copy.
- `src/components/booking/OrderSummary.tsx`, `BookingPanel.tsx` — a "Delivery fee" line in the breakdown when delivery is selected.
- `src/components/booking/Step4Confirmation.tsx` — receipt row, conditionally rendered so pre-migration bookings (₱0) do not show a spurious line, matching how `035` handled the protection fee.

**Existing listings** default to `null` — no host is retroactively opted into delivery they never agreed to offer.

**Refunds need no change.** `refundBooking()` refunds against the charged `total_amount`, which now includes the delivery fee — the correct behavior, since the renter did pay it.

**Standing obligations checked.** `AGENTS.md` requires every new table to enable RLS in its creation migration, and every new table or new PII column on `profiles` to be added to the account-deletion route. This work adds **no new table and no new `profiles` column** — `delivery_fee` lives on `listings`/`bookings` and is not personal data — so neither obligation is triggered. Recorded here so the check is visibly done rather than silently skipped.

## 6. GCash / Maya

### Problem

Per the project record (checked 2026-08-31), `gcash`, `maya`, and `card` all show **Submitted** on the live PayMongo account, awaiting KYB approval; only `qrph` is **Active**. The application code is the same `PaymentIntent → PaymentMethod → attach` path `qrph` uses successfully, and it was verified end-to-end in test mode. **This is an account activation issue, not a code defect** — treated as confirmed and not re-probed, per the design decision.

### Design

No change to the payment code path. The work is making the failure honest instead of silent.

- **Env-driven availability.** A `NEXT_PUBLIC_DISABLED_PAYMENT_METHODS` comma-separated list marks methods unavailable. `Step3Payment.tsx` already has a `comingSoon` flag on `BASE_METHODS` (used today for Apple Pay / Google Pay), so this reuses the existing disabled-tile rendering. GCash and Maya get a "Temporarily unavailable" state rather than a dead end. When PayMongo activates the methods, clearing the env var re-enables them **with no code deploy**.
- **Default method.** `Step3Payment` currently initializes `useState<PaymentMethod>('gcash')`. This must fall back to the first *enabled* method (QR Ph today), or checkout opens pre-selected on a disabled tile.
- **Clearer rejection.** When PayMongo rejects an inactive method, the checkout route surfaces a specific message instead of a generic failure.

**Adjacent fix in the same file.** `Step3Payment.tsx:382` renders the promo-code Apply button as `bg-[#FDF0D5] … text-white` — white text on the cream accent, effectively invisible. This is the same contrast class fixed in `684d9ad`, missed at this site. Corrected while working in this file.

## Verification plan

Each workstream is verified live against the hosted database before being called done, following the project's established e2e pattern (demo accounts, forged SSR cookie, service-role cleanup).

1. **Category** — create a listing in the new category through the wizard; confirm it saves, appears under the search filter, and round-trips through the edit page.
2. **Locations** — confirm the dropdown lists all 82 provinces; confirm a Naga City / Camarines Sur listing pins in Naga rather than Manila on both the listing detail and search maps; confirm existing `province: 'Other'` rows still resolve.
3. **Wizard idempotency** — inject a forced failure at step 3, 4, and 5 in turn; confirm each retry produces exactly **one** listing row and does not re-upload photos.
4. **Verification gate** — confirm an unverified host's new listing is invisible to an anonymous visitor and to search; confirm a direct client-side `is_draft = false` update is rejected; confirm approving the ID in `/admin` publishes the pending listings; confirm the seed listings stayed live through the migration.
5. **Delivery fee** — call `create_booking` for a delivery booking and assert `total_amount` equals `rental − discount + service + delivery + deposit` exactly; assert a pickup booking on the same listing charges no delivery fee; assert a delivery booking against a `null`-fee listing is rejected; assert `request_payout()` includes the delivery fee in the host's balance.
6. **Payments** — confirm the disabled tiles render, the default selection lands on an enabled method, and QR Ph checkout still completes.

`npm run build` and `npm run lint` clean at the end of each workstream.

## Out of scope

- **Distance-based or per-booking delivery quoting.** The flat per-listing fee was chosen deliberately; per-booking quoting would mean a booking's total changes after creation, which conflicts with the immutable-amounts model.
- **Per-listing admin approval.** The gate is on host identity only, not on individual listings.
- **Re-probing the PayMongo account status**, per the design decision above.
- **Live geocoding.** The static table was chosen specifically to avoid a runtime dependency.
